Project: AI Sound Advisor

Goal:
Build a real-time AI assistant that monitors a Behringer X32 mixer and live audio,
analyzes sound quality, and provides prioritized, human-friendly suggestions to a sound engineer.

***SYSTEM OVERVIEW
The system must:
- Continuously operate in the background
- Analyze both mixer data (OSC) and audio (main + room mic)
- Detect sound issues (clipping, vocal masking, EQ problems, loudness, etc.)
- Generate clear, instructor-style recommendations
- Learn user preferences over time via profiles
- Avoid overwhelming the user with excessive suggestions

***TECHNOLOGY STACK

Language:
- Python (primary backend)

Audio Processing Libraries:
- librosa → FFT, spectral analysis
- pyloudnorm → LUFS loudness calculation
- numpy → numeric operations
- scipy → signal processing

Audio Input:
- sounddevice OR PyAudio (for real-time audio capture)

OSC / X32 Communication:
- python-osc (UDP/OSC communication with X32)

AI / LLM:
- Mistral 7B (local model)
- Run via:
  - Ollama OR
  - LM Studio API

Web Backend:
- FastAPI (preferred)
- OR Flask (simpler alternative)

Frontend:
- React (preferred long-term)
- OR simple HTML + JavaScript (V1 prototype)

Real-time Communication:
- WebSockets (preferred)
- OR HTTP polling (fallback)

Data Storage:
- JSON files for profiles and logs (V1)
- Optional: SQLite (future)

Optional Extensions:
- torchaudio (advanced audio processing)
- webrtcvad (voice detection)

AGENT ARCHITECTURE
***AGENT 1: Audio Analysis Agent
Purpose:
Analyze incoming audio streams in real time.

Inputs:
- Main mix audio
- Room microphone audio
- Recorder Output (USB / bus / stream feed)

Responsibilities:
Calculate LUFS loudness using pyloudnorm
- Perform FFT frequency analysis using librosa
- Detect peaks using numpy/scipy
- Output structured metrics

Output Example:
{
  "loudness_lufs": -15,
  "peak_level": -1.2,
  "low_mid_energy": "high",
  "high_freq_energy": "normal"
}

***AGENT 2: Mixer State Agent (OSC)
Purpose:
Monitor and track X32 mixer state via OSC.

Inputs:
- X32 network connection (IP + UDP)

Responsibilities:
- Read channel levels (faders, gain)
- Read mute states
- Read channel labels
- Track buses, FX sends, etc.

Output Example:
{
  "channel_3": {
    "name": "Lead Vocal",
    "fader": -10,
    "mute": false
  }
}

***AGENT 3: Detection Engine
Purpose:
Combine audio + mixer data to detect sound issues.

Inputs:
- Audio metrics (Agent 1)
- Mixer state (Agent 2)
- Profile data

Responsibilities:
- Detect:
  - Feedback risk
  - Vocal masking
  - Clipping
  - Loudness issues
  - EQ problems (mud, harshness, frequency range)
- Assign priority
- Calculate confidence score

Output Example:
{
  "issue": "vocal_masking",
  "channel": "Lead Vocal",
  "priority": "high",
  "confidence": 0.9
}

CONFIDENCE CALCULATION

Factors:
- Signal strength
- Duration of issue
- Agreement between:
  - Room mic
  - Board data
- Consistency over time

Output:
- High (>0.8)
- Medium (0.5–0.8)
- Low (<0.5)

***AGENT 4: Suggestion Generator (LLM — Mistral 7B)
Purpose:
Convert structured issues into clear, instructor-style guidance.

Inputs:
- Issue objects from Detection Engine

Responsibilities:
- Generate short, actionable suggestions
- Maintain instructor tone
- Provide optional detailed explanation ("More")
- Provide step-by-step instructions ("Tell me how")

Example Output:
"Channel 3 vocals are slightly buried under music. Increase the vocal level or reduce band levels slightly."

Example (Tell Me How):
1. Select Channel 3
2. Raise fader by 2–4 dB
3. Adjust EQ if needed

***AGENT 5: Context & Profile Agent
Purpose:
Store and apply learned knowledge and environment configuration.

Responsibilities:
- Manage profiles (load/save)
- Store user instructions and overrides
- Track "normal" conditions
- Apply learned behavior

Profile Contents:

***AGENT 6: Suggestion Pacing Agent
Purpose:
Control the timing and frequency of suggestions.

Rules:
- New issue → immediate suggestion
- Ongoing issue → repeat every 10–30 seconds
- After user change → pause 2–4 seconds
- No issues → display:
  "Your mix is sounding good"

Prevents excessive or rapid suggestions.

***NETWORK CONNECTION / X32 CONNECT WORKFLOW
(In simple English — how the dashboard connects to the mixer.)

There is an "X32 Network" panel on the dashboard with a box for the mixer's
IP address, a box for its port (default 10023), a Connect button and a
Disconnect button. The IP and port boxes start filled in with the values the
system was configured with, so usually the operator just clicks Connect.

What happens when you click Connect:
1. The system sends a small OSC message called "/info" to the IP and port you
   typed. This is like saying "Hello, who are you?" to the mixer.
2. The mixer answers with its details (server version, name, model and
   firmware version). The system reads that answer and shows it in a status
   label, for example: "Connected to: X32 Firmware 4.06".
3. If the mixer does not answer (wrong IP, cable unplugged, mixer off), the
   system does NOT crash. It simply shows a warning in the same label, such as
   "No response from 192.168.0.2:10023. Check the network connection." The rest
   of the dashboard keeps running.

Staying connected (keepalive):
- The X32 only keeps sending us its live changes for about 10 seconds at a
  time. So while we are connected, a background helper quietly re-sends another
  OSC message called "/xremote" every 9 seconds. This keeps the mixer streaming
  its updates to us without a gap.
- If that background message ever fails (the mixer drops off the network), the
  system handles it gracefully: it stops the helper, marks the connection as
  lost, and shows a warning in the status label. Nothing crashes.

Disconnect:
- Clicking Disconnect stops the background helper and closes the connection
  cleanly. The status label goes back to "Not connected".

Where this lives in the code:
- src/x32_connection.py     -> the connection logic (send /info, read the
  reply, run the /xremote keepalive, handle drops). Uses the python-osc
  library and is fully testable without real hardware.
- src/web_server.py         -> the buttons talk to it through three endpoints:
  /api/x32/connect, /api/x32/disconnect and /api/x32/status.
- src/templates/index.html  -> the "X32 Network" panel (IP/port boxes, the two
  buttons and the status label).

PERFORMANCE REQUIREMENTS

- Audio analysis must run in real time (≤ 50 ms per cycle)
- AI (LLM) must NOT run every loop
  - Only trigger on new or changed issues
- System must remain responsive while running other software (e.g., ProPresenter)
